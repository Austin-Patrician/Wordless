## 目标

得到一份**能继续改的界面设计**，而不是一张图或一段 HTML 片段。设计是一份工作区里的设计包：`design.json`（画布清单）、`theme.css`（设计令牌）、`frames/` 里的每个 `.html` 文件是一屏界面。Agent 负责写这些文件，你负责在画布上缩放、选择、对齐、换色和导出。

## 在画布上完成设计闭环

右侧画布不是最终结果的静态截图，而是当前会话的工作界面。Agent 写完一屏，画布就渲染出真实像素；你在画布上做的几何改动（移动、缩放、对齐、分布）记在清单里，**不会回写进帧源码**，所以下一次让 Agent 改这一帧时，它改的是内容，不是你在画布上摆好的位置。

分工只有一条要记住：**画框由你加，框里的东西由 Agent 写。** Agent 手上没有"新建画框"的工具（它只有读状态、建包、质检、截图和风格那几条），因为"这里还要一屏"是设计判断，不是它能替你决定的。

<Steps>
1. 在新建页的 **挑一套风格开始** 里选一套内置风格。选 **自己定** 就等于不指定风格，Agent 会按你的描述发挥，也可以反问你。
2. 直接描述你要的界面：几屏、每屏做什么、给谁看、有哪些必须出现的内容。
3. Agent 调用 `design_create` 建出设计包，第一帧已经带上那套风格的令牌与规范；你选过的风格会跟着第一条消息一起送到。
4. 在右侧画布上查看第一帧。用 **选择**、**抓手**、缩放按钮（放大、缩小、适应内容、回 100%）检查布局。
5. 需要下一屏时，用 **新建画框** 自己加一个，再让 Agent 写它。
6. 选中一帧，用 **让 agent 改这一帧** 把这一帧作为上下文送进对话，然后描述要改什么。
7. 打开 **色彩系统** 看这份设计的令牌（来自 `theme.css`）；点一个色块就能把它递给对话，让 Agent 用它。
8. 需要整体换风格时用 **应用**；已写好的画框会按新规范返工，因为旧画框里写着旧令牌。
9. 某一屏定了，用 **导出渲染图** 把它合成图（PNG / 长图 / PDF，可加设备外壳），或者用 **下载素材** 取走图片、规范与素材文件。
</Steps>

## 完整制作流程

<Prerequisites>
- 模型必须同时支持工具调用与图片输入：质检闭环的第二步是**看渲染出来的像素**，不支持图片的模型只能凭标记猜版式
- 一个可写的工作区；设计包会建在工作区里
- 可选：品牌色、参考截图、竞品链接

</Prerequisites>

<Steps>
1. 引用现有的设计说明、文案或参考图，明确平台和尺寸（手机 390×844、笔记本 1440×900）。
2. 让 Agent 先建包（`design_create`，带上你选的风格）并只写第一屏，不要一次写三屏。
3. 结构写完让它跑 `design_inspect`：它做的是确定性检查（内容溢出、文字被裁、nowrap 文字超出父级、行内元素超出、被父级裁掉的表面），返回的是坐标事实而不是评价。
4. 检查通过后再让它 `design_screenshot` 看真实像素——字号、间距、对齐、颜色这些从标记里看不出来。
5. 修完再看一次。这个"检查 → 看图 → 修"的闭环有轮次上限，别用它替代你自己的想法。
6. 每加一屏重复第 2 到第 5 步；在画布上对齐、分布、重命名，整理画布。
7. 需要换风格就 **应用** 一套新的；接受"旧画框要按新规范返工"这件事，然后让 Agent 逐帧改。
8. 完成后 **下载素材**，把图片与规范文件交给下一环。

</Steps>

</PromptBlock>

<ApprovalCheckpoint risk="medium">设计工具会在工作区里写文件和覆盖内容：`design_create` 建目录，`design_style_apply` 覆盖 `theme.css` 与 `DESIGN.md`（覆盖前会整份备份到 `.build/style-backup/`）。确认目标设计包路径，别批准它对不是你要改的那份动手。</ApprovalCheckpoint>

## 导出：渲染图与素材

画布上有两个导出入口，用途不同：

- **导出渲染图**：把选中的画框合成一张图。格式有 PNG、长图、PDF；每页放 1 到 4 帧，超出自动分页。设备外壳（圆角、边框厚度与颜色）、背景或透明底、投影、Wordless 水印、导出倍率都可以调。画框从右侧轨道拖进来，顺序就是图里的顺序。**这些设置只影响这一张导出图，不改设计本身**——导出不会动 `theme.css`，也不会写回帧。
- **下载素材**：打包这份设计的图片、规范与素材文件，给开发和交付流程用。

## 设计包里有什么

| 路径 | 作用 | 谁负责 |
| --- | --- | --- |
| `<名称>.wdesign/design.json` | 画布清单：有哪些画框、尺寸、以及你在画布上做的几何改动 | 工具写，不要手改 |
| `<名称>.wdesign/theme.css` | 设计令牌：颜色、间距、字号。**唯一真源** | 由风格写入；不要手写 |
| `<名称>.wdesign/DESIGN.md` | 写给 Agent 的规范：这套风格怎么用 | 由风格写入 |
| `<名称>.wdesign/frames/*.html` | 每个文件是一屏界面，开头用注释声明自己的尺寸与标题 | Agent 写 |
| `<名称>.wdesign/.build/` | 构建与备份产物 | 工具管理 |

帧里引用的是相对路径（`../theme.css`、`../assets/...`），渲染时用的是同一套相对路径，所以不要改写它们。帧开头的尺寸声明（`<!-- @frame { "width": 390, "height": 844, "title": "Home" } -->`）不要删——画布用它的标题给画框命名。

## 内置风格

内置风格库当前有 29 套，覆盖从 Linear、Stripe、Notion、Apple 到 claymorphism、glassmorphism、复古 95 这类视觉方向。每套风格包含一组颜色令牌和一份写给 Agent 的规范，所以"换风格"不是把颜色换一遍，而是换掉这份设计要遵守的体系。

- 新建时选风格最省事：令牌在建包时就写好了，第一帧出生即正确。
- 已经画了一半再 **应用** 风格：`theme.css` 与 `DESIGN.md` 会被覆盖（先整份备份），而**已经写好的画框仍然带着旧令牌**——界面会告诉你几帧需要返工，然后由 Agent 按新规范逐帧改。
- 让 Agent 自己挑风格是下策。没选风格时它会先列几套让你选，而不是替你决定。

## Wordless 的差异

大多数"生成 UI"的流程在给你一段 HTML 或一张截图时结束；Wordless 把设计留在工作区里继续改。画框是真实 HTML，颜色来自令牌而不是写死的十六进制值，Agent 有确定性的版式检查和"看真实像素"两条质检手段，而你在画布上的几何改动不会被下一轮生成冲掉。

| 场景 | Wordless 中的操作 | 验收方式 |
| --- | --- | --- |
| 从描述开始做一套界面 | 先选风格，再建包，逐屏写 | 每屏只解决一件事，颜色全部来自令牌 |
| 只改一屏里的一个区块 | 选中该帧，把这一帧作为上下文发指令 | 其余画框与画布位置不变 |
| 品牌换色或换风格 | 应用新风格，再按规范返工已有画框 | 全篇令牌一致，没有残留的旧颜色 |
| 交接给开发 | 下载素材或直接引用工作区里的设计包 | 帧是可直接打开的 HTML |

## 常见恢复

- 画框比内容小：画框是固定尺寸的画布，内容溢出不等于画布变大。先加宽画框，或者让 Agent 精简内容。
- 界面看起来没有样式：样式表没编译出来。这属于安装或打包问题，不是设计写错了——升级到修复版本，不要把精力花在给帧里手写样式上。
- 帧里出现写死的颜色值：让它改用 `theme.css` 的令牌。写死的颜色不会跟着风格走。
- 风格 id 不存在：`design_style_apply` 会拒绝并列出真实可用的 id；直接把显示出来的那个 id 交给它。
- 找不到设计包：路径是相对工作区的，且目录名带 `.wdesign` 后缀。让 Agent 先调 `design_status`（不带 `path`），它会把工作区里真实存在的设计列出来。
- 想让 Agent 直接加画框：它做不到，也不该做。用画布上的 **新建画框**。
